Every component takes these names from reiwand_core::dbus. The command line client (reiwand-ctl) and the desktop app are plain clients of this interface: every action is available in both. The system tray and the desktop integration offer a subset.

Item Value
Bus session
Well-known name io.github.reiwand.Daemon
Object path /io/github/reiwand/Daemon
Interfaces io.github.reiwand.Daemon1, Library1, Playlists1, Profiles1, Providers1, Repos1, Inputs1, Publish1, Accounts1, Carry1, all on that object

The daemon is D-Bus activatable (packaging/dbus) and runs as the systemd user unit reiwandd.service. In the Flatpak (packaging/flatpak) it owns the name through --own-name, so Flatpak exports the same activation file, starts the daemon with flatpak run and drops SystemdService; there is no systemd unit there. The name is owned without allowing replacement. A second daemon checks the name before initializing the GPU and PipeWire and exits at once with an error saying that another reiwandd owns it.

Every connection of the workspace to the session or the system bus (daemon, reiwand-ctl, the app) goes through reiwand_client::bus, which sends each authentication command only after the bus answered the one before. Inside the Flatpak both buses are reached through xdg-dbus-proxy, and its releases before 0.1.6 drop a client that sends its authentication commands in one write; with this handshake the daemon and the clients connect through any proxy version. Those releases also drop a client whose message serials do not increase strictly, and the bus library numbers a message when it builds it, not when it writes it; so after the handshake the adapter gives every outgoing message the next serial of its connection, in the order the messages reach the socket, and gives each reply back the serial of the call it answers. scripts/integration-proxy.sh checks both when REIWAND_BUS_PROXY names a proxy binary, restarting the daemon fifteen times behind it.

A panic in any thread of the daemon, a lost GPU device, a GPU that stops responding or a Wayland protocol error from the compositor makes the daemon exit with status 70 at once, without running the exit handlers of the libraries it uses (a GPU driver that stopped answering cannot hang it there), and the end of the display server connection with status 0 the same way; the user unit restarts it (Restart=on-failure, at most 5 starts in 60 s) and clients get their streams again through RequestStream. Only the methods that change what is shown (Library1.Apply, Playlists1.Start, Stop, Next and Previous, Profiles1.Activate and the Daemon1 methods that change something) need the renderer: while it is not running they return Failed (the renderer stopped after an error; restart reiwandd) and change nothing. Every other method keeps working. Debug builds started with REIWAND_RENDER_STOP=1 stop their renderer on SIGUSR2, so tests can check this.

The daemon opens network connections only to the providers, repositories and the servers the user added (the accounts they signed in with) (including the signed mirrors of a repository, the only hosts a repository request may be redirected to), with a generic User-Agent: reiwand/<version> (+https://github.com/reiwand/reiwand) (the program and the address of the project, nothing about the person or the computer) and without cookies or Referer. At startup it contacts only providers due for their automatic sync; the daily repository refresh starts 10 minutes later.
